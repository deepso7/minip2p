# Stream keys and an Endpoint-owned write queue

Three things made application streams awkward on the Endpoint ([plan](../plans/dx-perf-size-evolution.md), Decisions 1.2, 3.1 and 3.2). A stream id is unique only per connection, so every stream operation took `(conn_id, stream_id)` and every stream event carried both, and applications defined their own tuple key. The bare `send_stream` reported a partial write as `Err(DriverError::Full { unsent })`, so `?` on it silently dropped the unsent tail. And the fix for that, the `StreamWriter` sidecar, had to see every event (`observe`) to resend tails and notice ended streams; applications forgot to feed it, swept `is_pending` to detect dropped writes, and ffi-core and the web host each wrapped it again. ADR 0029 made one `Endpoint<P>` surface, so each fix is now written once. We decided:

- **`StreamKey` names a stream.** It lives in `minip2p-transport`, wraps a `ConnectionId` and a `StreamId` (`conn_id()`, `stream_id()`), and is `Copy`, ordered, hashable, and displayed as `<conn>/<stream>`. `Endpoint::open_stream` returns one; `send_stream`, `try_send_stream`, `close_stream_write`, `reset_stream`, `abandon_stream` and `stream_consumed` take one; every Endpoint stream event carries `stream: StreamKey` in place of the two fields, and keeps `peer_id`, since `peer_of(conn)` can fail once the connection is gone. The swarm and the transports keep their separate ids: their APIs are per-connection already, and a key there would churn every transport for nothing. ffi-core and the bindings flatten it back into `conn_id` and `stream_id`, so the TypeScript surface is unchanged.
- **The bare write is `try_send_stream`, returning `Result<SendOutcome, DriverError>`.** `#[must_use] SendOutcome` is `Accepted` or `Full { unsent }`. A partial write is an outcome, so `?` propagates only real failures and the tail can no longer be dropped by accident.
- **The Endpoint owns a bounded write queue, and `StreamWriter` is gone.** `send_stream(stream, data) -> Result<(), SendError>` sends what fits and queues the rest, within a byte budget shared by every stream (`write_budget(bytes)` on the builders, `DEFAULT_WRITE_BUDGET` = 8 MiB). The engine follows each swarm event before queueing it: a Writable for a stream with queued bytes resends them (and is consumed, since the queue owned that tail), and once they are all accepted the engine sends a deferred FIN and queues `StreamWriteAccepted { peer_id, stream }`; a `StreamWriteStopped`, `StreamClosed`, `ConnectionClosed` or `ConnectionReplaced` drops what was held for it and queues `StreamWriteAborted { peer_id, stream, unsent }` right after. A resend that fails waits for that terminal event later in the batch, and aborts at the batch's end only if none came, so the abort never precedes the event that explains it. Closing the endpoint aborts every queue still held, in the close report, since a connection the transport has not finished closing drops its bytes too. `close_stream_write` behind queued bytes defers its FIN, and later writes fail with `SendError::Closing`. `reset_stream` aborts the stream's queue (with the abort event), `abandon_stream` drops it silently along with every other event for the stream. ffi-core and the web host delegate to it, with an unbounded budget, and keep only their one-pending-write-per-stream check, after the deferred-close check (`is_write_closing`), so a write behind a deferred FIN stays `InvalidState` rather than backpressure. An empty write behind queued bytes is accepted without queueing anything.
- **StreamWriter's semantics move unchanged where they still apply.** A payload is admitted whole against the budget or refused whole, unsent (`OverBudget`, retryable; `TooLarge`, past the whole budget); the budget counts payload lengths with the ADR 0012 retained-slice rule (`retain_slice` copies a tail out once it shrinks below half its allocation); a refused FIN or a failed resend means the stream already ended, whose own event reports it. What changes is the one-pending-write limit: a write behind queued bytes is appended whole instead of refused as `Busy`, since the queue keeps call order and the budget already bounds memory.

## Rejected alternatives

- **Keeping `StreamWriter` and fixing only its ergonomics.** Any sidecar has to see every event, which is the mistake applications kept making; inside the engine it sees each swarm event before the application does, and nothing has to be fed.
- **One pending write per stream (StreamWriter's `Busy`) in the Endpoint.** It made "send all of this" fail on the second call. Hosts that want that discipline (the bindings, whose SDK settles one write at a time) check `is_write_pending` themselves.
- **`StreamKey` through the swarm and transport traits.** No caller there gains anything; every transport and test transport would change.
- **Surfacing `StreamWritable` for queued streams as well.** The application holds no tail for them; it would only invite a second, out-of-order write. The exception is a stream whose `try_send_stream` returned Full: that caller holds a tail and waits for a Writable, so the queue re-emits the one it consumed after its `StreamWriteAccepted` (unless a deferred FIN closed the write side).

## Consequences

- `send_stream` changed meaning (it used to be the bare write). Code that matched `Err(Error::Full { unsent, .. })` moves to `try_send_stream` and `SendOutcome::Full`; code that wrapped `StreamWriter` calls `send_stream` and listens for `StreamWriteAccepted` / `StreamWriteAborted`.
- With the default budget, a single payload over 8 MiB is refused as `TooLarge`; split it or raise the budget. `write_budget(0)` costs nothing beyond an empty map, for callers that use `try_send_stream` only.
- While a stream has queued bytes, `try_send_stream` on it accepts nothing and returns the whole payload as `Full`, and its Writable is reported as `StreamWriteAccepted` (then passed on to a bare caller still waiting for it), so bytes never reorder. Once a write-side close is deferred behind them, `try_send_stream` fails with `SwarmError::WriteClosed` instead: no Writable follows a FIN.
- `send_stream` is the hottest path; with nothing queued it adds one map lookup and the admission check to the bare write.
