# HTTP/3 and QPACK: only the WebTransport subset, validated strictly

Both ends of WebTransport implement only the HTTP/3 and QPACK subset libp2p WebTransport needs (ADR 0023): `WtSession` on the server (`minip2p-quic`) and the `h3` and `qpack` modules of the browser client (`minip2p-webtransport`). Neither uses a dynamic QPACK table, and both enforce RFC 9114, RFC 9204 and the WebTransport drafts on what they do implement rather than tolerating what they do not.

## Server: `WtSession`

- **Control stream.** SETTINGS must come first, checked by frame type so a skipped unknown frame before SETTINGS fails too. Setting legality (boolean settings are 0 or 1, HTTP/2-only settings) is checked before any draft is chosen, so a bad value fails even beside a valid offer. A smaller MAX_PUSH_ID fails; since we never send PUSH_PROMISE, no push ID was ever promised, so any CANCEL_PUSH is `H3_ID_ERROR` (RFC 9114 §7.2.3).
- **QPACK.** The table capacity is 0, so every encoder-stream instruction is illegal; on the decoder stream only Stream Cancellation is legal, since we never insert. Pseudo-headers come first, so `:authority` is known when `host` is checked against it.
- **Peer unidirectional streams.** Only a server may open a push stream (RFC 9114 §6.2.2). A session ID is a CONNECT stream's ID, client-initiated bidirectional and so a multiple of 4; any other cannot name a session at all (draft-14 §4) and is `H3_ID_ERROR`, unlike a valid ID that is not ours. Other WebTransport and unknown (including GREASE) stream types are stopped with `H3_STREAM_CREATION_ERROR`, never fatal. A stream that ends before saying what it is is dropped and our unused side is reset (`H3_REQUEST_INCOMPLETE`) so the stream is freed.
- **CONNECT stream.** Trailers end the message (RFC 9114 §4.1): DATA or HEADERS after them fails. A FIN must fall between frames and between capsules; a reset may cut anywhere. The connection carries one session, so a session flow-control error closes the connection.

## Client: `minip2p-webtransport` codecs

- **QPACK is static-table only.** `QpackDecoder` rejects any field section with a non-zero Required Insert Count and any dynamic or post-base reference; it also rejects a set Delta Base sign bit, since with Required Insert Count 0 that would make the Base negative (RFC 9204 §4.5.1.2). `DecoderStreamReader` accepts only Stream Cancellation instructions (integers capped at 2^62); Insert Count Increment and Section Acknowledgment refer to a dynamic table the encoder never uses and are errors. The encoder always emits Required Insert Count 0 and Base 0.
- **Decoded size is capped, not just encoded size.** Name and value bytes, counted with RFC 9204's 32-byte per-field overhead, may fill only what `MAX_FIELD_SECTION_SIZE` (8 KiB) leaves, so a small Huffman-coded HEADERS frame cannot expand past it. Huffman padding must be a prefix of EOS of at most 7 bits (RFC 7541 §5.2).
- **The tables are transcribed from the RFCs**: `STATIC_TABLE` from RFC 9204 Appendix A, `HUFFMAN_CODES` from RFC 7541 Appendix B (code aligned to the LSB, bit length, EOS last).
- **`FrameDecoder` never trusts a declared length.** Its buffer grows with what arrives, so a length claim reserves nothing; oversized known frames are rejected before buffering and unknown (GREASE) frames are skipped without buffering. A zero-length DATA frame is reported rather than skipped, so callers can reject DATA where RFC 9114 forbids it whatever its length. Data chunks leave the decoder at a frame boundary as soon as the last chunk is returned. After a `WEBTRANSPORT_STREAM` header nothing more is framed, so the decoder parks in `Skip` and a stray `decode` cannot misparse application data.
