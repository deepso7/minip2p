# WebTransport client stream lifecycle against the browser

The browser client is split across a seam (ADR 0023): `JsIo` (`bindings/ts/web/src/io.ts`) turns the browser's `WebTransport` promises into queued `IoEvent`s, and `WebTransportClient` (`minip2p-webtransport` `client.rs`) reacts to them. Which promise reports what, and what the client does with it, is fixed so that every outcome is reported exactly once and nothing is left pending.

## JsIo: browser promises to IO events

- **Session ends come only from `transport.closed`.** A rejected `transport.ready` is ignored, because `closed` rejects too and reports it. `closed` fulfilling is `sessionClosed` with its close code; `closed` rejecting (never came up, or lost when the network goes away) is `sessionFailed`, not an orderly close. Likewise the incoming-stream accept loop swallows its error: the session ended and `closed` reports it.
- **Peer stream signals come from the stream's own `closed` promises.** The peer's STOP_SENDING errors the writer, so `writer.closed` rejecting with a stream code is `stopSending`; a rejected `closeWrite` rejects `writer.closed` too, after its own handler reported it, so the `writeEnded` flag keeps it to one event. The peer's RESET_STREAM errors the read side whether or not a read is pending, so `reader.closed` rejecting is a `reset`. When `writer.close()` is rejected with a coded error, `close()` and `writer.closed` both reject with it; still only one `stopSending` is reported. Firefox fails the read side with no stream code when the peer stops our sending as it closes. That case also ends as a `reset` (code 0).
- **Rust forgets a session's streams with the session.** `close` retires every stream of the session before calling `WebTransport.close()`, which silences their later callbacks. `close` may throw when the session is already closed. `quietly` swallows that, since `closed` reports the end anyway.
- **Chromium can report an orderly server close as an error.** When the CONNECT stream completes before Chrome reports the session closed, its network service sends `OnClosed` without the required `final_stats` and the renderer drops the message, so `closed` rejects with "Connection lost." and the SDK reports a `connectionClosed` error instead of a clean close (seen in Chrome 156 and current Chromium). The browser e2e test (`closes are orderly both ways`) accepts that reason on Chromium only. The server's half of the orderly close is covered natively by `a_server_close_keeps_quic_open_for_the_closing_phase`.
- **Lint allows two-callback `.then`.** Because these promise callbacks become queued events and nothing awaits them, `oxlint.config.ts` sets `promise/always-return` with `ignoreLastCallback` and `promise/catch-or-return` with `allowThen`. A fire-and-forget `.then(onFulfilled, onRejected)` handles both outcomes, and its final callback's return value has no consumer.

## WebTransportClient: reacting to the platform

Beyond ADR 0023 and ADR 0012:

- **The Noise stream is the client's own.** It produces no stream events; its bytes are not counted against the send caps; anything the server sends on it after the handshake is ignored. After message three the client queues the stream's FIN. A server FIN on it is a failure only before the server's messages are verified. A platform refusal of the Noise stream, a stop-sending before the connection is up (message three can no longer arrive), or a server reset all fail the handshake; a reset after it only ends the platform's wait for the Noise FIN.
- **Peer resets.** A caller stream's reset may be the browser's view of the session ending, so it is held for `SESSION_END_GRACE_MS` before being reported; a session end within the window stands for those held resets. When the peer resets its sending side, the client resets its own side too, as the QUIC server does, so the platform frees the stream. A reset of a stream already retired (both halves closed) ends the platform's wait for its FIN.
- **Stop-sending** means a FIN the stream may still hold can no longer be sent, and writes still with the platform are released, because a stopped stream never completes them; after `StreamClosed` nothing more is reported. A platform write refusal likewise drops the stream's remaining writes.
- **Receive accounting.** Data arriving after the read side ended is ignored. Acknowledging bytes of an ended connection releases them without granting credit, and abandoning a stream of an ended connection only settles it. Promoting a stream to control can open the reserve to a stream waiting on Full, so it wakes Writable.
- **CA-certificate dials carry no certhashes**; the platform verifies the chain (ADR 0024).
