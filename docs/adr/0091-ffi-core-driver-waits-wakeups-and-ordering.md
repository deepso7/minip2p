# ffi-core driver: waits, wakeups and event ordering

How the `minip2p-ffi-core` background driver (`driver.rs`, `endpoint.rs`) sleeps, wakes and orders what the binding sees:

- **The driver waits only through `Endpoint::wait(WaitDeadline::NEVER)`.** It keeps no deadline of its own: the wait already wakes for every timer the endpoint's transports, protocols and agents report and for input on every socket registered with its readiness poll (mDNS included), so an idle driver sleeps until something is due. A follow-up `poll()` is avoided because it would open a second batch, breaking the carry's Endpoint emission order. Every command, query and `stop` interrupts the wait; interrupts sent before one is reported coalesce, so a burst of commands costs one wake and the command queue is drained afterwards.
- **Events are published and ingested before `state` is released**, so no command runs between the endpoint emitting events and the carry holding them, and the doorbell never rings ahead of the published peer list.
- **Command/driver handshake.** `PendingCommand` counts callers waiting for `state`; its `Drop` uses `SeqCst` to pair with `wait_for_commands` (either the driver sees the decrement before waiting, or the decrement sees it waiting and notifies), and takes the `commands_idle` lock before notifying so the notify cannot fall between the driver's check and its wait. `start` registers a pending command so a second `start` finds the driver parked on the lock, and the driver parks on `state` until `start` returns.
- **`wait_stopped` sleeps on the stopped latch, not on `state`**, because an idle driver holds `state` until something is due, possibly never. A zero timeout is a pure poll and skips the thread-identity check, which would interrupt the driver.
- **Shutdown order.** Only a `stop` from `Created` releases the endpoint inline; a running driver releases it on exit. The pump returns only once shutdown has begun; if it panicked, the endpoint may be mid-update, so it is dropped rather than closed. Events produced by the closing drain (connection ends among them) reach the binding ahead of `EndpointClosed`.
- **Doorbell callbacks are advisory** and cannot stop event delivery (ADR 0003, amendments).
- **`abandon_stream` cannot lose a pending write.** The Endpoint drops a held tail only once it accepts the abandon, so a rejected call (a stale connection id) keeps it; the carry drops the stream's events only when the Endpoint accepted or the close was already handed over. The events lock is released before `stream_consumed` drives the Endpoint again to release dropped data bytes (moot after a reset or settlement).
