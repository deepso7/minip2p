title: Drive events
description: Use one Endpoint::wait loop for every event, including NAT, pubsub, discovery, and relay-server output.
---

minip2p remains caller-driven at every layer. The application chooses when to poll, how long to wait, and which events to handle. Read [where events go](/rust/concepts#where-events-go) first. If you are working with custom streams, also read [Register a protocol](/rust/register-a-protocol).

## Pick a driving method

The endpoint has one ordered event stream and two ways to read it. `Endpoint::wait` blocks until an Endpoint event, the caller's deadline, or an interruption; `poll()` drains whatever is ready without blocking. Enabled capabilities (NAT, pubsub, discovery, relay server) deliver their output as variants on the same stream, so one loop sees every event exactly once for every feature combination. Both use transport readiness when supported. Each call drives only its own endpoint, so blocking on one endpoint can delay others sharing the same thread.

| Method | Behavior | Good fit |
| --- | --- | --- |
| `wait(deadline)` | Drive until one `EndpointWaitOutcome`: `Event(EndpointEvent)`, `Deadline`, or `Interrupted`. | Every blocking application loop; correlating an operation while dispatching others |
| `poll()` | One non-blocking drive; returns currently available Endpoint events, finishing each swarm event the same way `wait` does. | Existing game, UI, or reactor loops |

## Deadline forms

Every endpoint wait accepts `impl Into<Deadline>`:

```rust
use std::time::{Duration, Instant};

use minip2p::Deadline;

let relative = Duration::from_secs(5);
let absolute = Instant::now() + Duration::from_secs(5);
let forever = Deadline::NEVER;
```

An already-passed absolute `Instant` deadline returns `Deadline` from `wait` before delivering another queued event. Relative `Duration` deadlines — including `Duration::ZERO` non-blocking drains — still inspect buffered events and poll once. The endpoint does not sleep or poll repeatedly past the deadline.

## Wait for a correlated outcome

Operations return IDs; wait for the matching event in your own loop:

```rust
use std::time::Duration;

use minip2p::{ConnectOutcome, Endpoint, EndpointEvent, EndpointWaitOutcome};

fn connect_to(
    node: &mut Endpoint,
    target: minip2p::PeerAddr,
) -> Result<(), Box<dyn std::error::Error>> {
    let connect_id = node.connect(target)?;
    let deadline = std::time::Instant::now() + Duration::from_secs(10);
    loop {
        match node.wait(deadline)? {
            EndpointWaitOutcome::Event(EndpointEvent::ConnectSettled {
                connect_id: settled,
                outcome: ConnectOutcome::Connected { .. },
                ..
            }) if settled == connect_id => return Ok(()),
            EndpointWaitOutcome::Event(EndpointEvent::ConnectSettled {
                connect_id: settled,
                outcome,
                ..
            }) if settled == connect_id => {
                return Err(format!("connect failed: {outcome:?}").into());
            }
            // Unrelated events keep flowing: dispatch them as usual.
            EndpointWaitOutcome::Event(event) => println!("{event:?}"),
            EndpointWaitOutcome::Interrupted => {}
            EndpointWaitOutcome::Deadline => {
                node.cancel_connect(connect_id);
                return Err("connect did not settle".into());
            }
        }
    }
}
```

The deadline bounds only this wait. Abandoning a wait never cancels the attempt, which keeps running and still settles; `cancel_connect` is the explicit stop.

With the `nat` feature, `connect` races direct candidates against a relay leg when one is configured. `EndpointEvent::Nat(NatEvent::PathEstablished { connect_id, .. })` reports the first usable path (the provisional Relayed path, when that lands first); `ConnectSettled` is the attempt's terminal. Match `PeerReady` only when the application needs Identify's protocol list (for example early `RemoteDoesNotSupport` checks). `open_stream` is allowed once the peer is connected; Identify is not a stack gate for opening known app protocols.

## Application event loops

Prefer `wait` and dispatch unrelated events while correlating an operation:

```rust
use std::time::{Duration, Instant};

use minip2p::{Endpoint, EndpointEvent, EndpointWaitOutcome};

fn run(mut node: Endpoint, peer: minip2p::PeerId) -> Result<(), minip2p::Error> {
    // One absolute deadline for the whole correlated wait — recreating a
    // relative Duration inside the loop would reset the timeout on every
    // unrelated event or interruption.
    let deadline = Instant::now() + Duration::from_secs(5);
    loop {
        match node.wait(deadline)? {
            EndpointWaitOutcome::Event(EndpointEvent::PeerReady { peer_id, .. })
                if peer_id == peer =>
            {
                println!("ready={peer_id}");
                break;
            }
            EndpointWaitOutcome::Event(EndpointEvent::Error(error)) => {
                eprintln!("runtime error: {error:?}");
            }
            EndpointWaitOutcome::Event(_) => {
                // Handle unrelated connection / stream / ping / capability events.
            }
            EndpointWaitOutcome::Deadline => break,
            EndpointWaitOutcome::Interrupted => {
                // Service external commands, then continue.
            }
        }
    }
    Ok(())
}
```

The endpoint has no second queue, so a correlated wait never buffers or drops unrelated events: each one comes back to your loop in order. Handle a busy source (such as a chatty stream) where it arrives rather than ignoring it.

Synchronous method failures are returned as `minip2p::Error`. Non-fatal problems that occur later while driving appear as `EndpointEvent::Error` or a capability failure event such as `EndpointEvent::RelayServer(RelayServerEvent::Error { .. })`.

## Stream and connection shutdown

- Call `close_stream_write` after the final byte for a graceful half-close.
- Call `reset_stream` when the peer should observe abrupt termination and the application still wants terminal events.
- Call `abandon_stream` when no matching buffered or future events should be delivered.
- Call `disconnect` to close the active peer connection.

`Endpoint` does not run a background shutdown sequence after it is dropped. Drive any graceful application-level close exchanges before leaving scope, then call `endpoint.close()?`. `close` consumes the endpoint, disconnects peers, and briefly drains the resulting events. Dropping also disconnects, but ignores errors.

With the `mdns` feature, `endpoint.shutdown()` has a narrower meaning: it sends mDNS goodbyes and stops mDNS while leaving QUIC and TCP usable.

## Wait for every event family

`wait` delivers ordinary and capability events on one stream. `EndpointEvent` is `#[non_exhaustive]`, so keep a wildcard arm:

```rust
use std::time::Duration;

use minip2p::{EndpointEvent, EndpointWaitOutcome, GossipsubEvent, NatEvent};

loop {
    match endpoint.wait(Duration::from_millis(250))? {
        EndpointWaitOutcome::Event(EndpointEvent::Gossipsub(GossipsubEvent::Message { data, .. })) => { /* ... */ }
        EndpointWaitOutcome::Event(EndpointEvent::Nat(NatEvent::RelayReserved { relay, .. })) => { /* ... */ }
        EndpointWaitOutcome::Event(EndpointEvent::ConnectSettled { connect_id, outcome, .. }) => { /* ... */ }
        EndpointWaitOutcome::Event(_) => {} // EndpointEvent is non-exhaustive
        EndpointWaitOutcome::Deadline | EndpointWaitOutcome::Interrupted => {}
    }
}
```

Capability variants exist only when their feature is enabled: `Nat` (`nat`), `Gossipsub` (`pubsub`), `Discovery` (`discovery` / `mdns`), and `RelayServer` (`relay-server`). `poll` and `wait` finish each swarm event before the next: that swarm event, then capability events in relay-server, NAT, Gossipsub, Discovery order, then Connection-attempt terminals (`ConnectSettled`). No order is promised between concurrently racing Transport candidates. NAT attempt terminals (`ConnectFailed`, `FellBackToRelay`) never appear; `ConnectSettled` carries the outcome. A `PathUpgraded` can still follow its attempt's `ConnectSettled` when the attempt settled on a provisional Relayed path. Embedded endpoints emit the same variants and do not use this step order.

State snapshot getters such as `path`, `reachability`, `active_reservation`, and `known_peers` stay authoritative for durable state. They may be ahead of the event stream, never behind their own emitted transition.
