# Bench CI mechanics: baseline storage and PR comments

Research for [Research: PR-comment and baseline-storage mechanics for a homegrown bench workflow](https://github.com/deepso7/minip2p/issues/127), against:

- official GitHub Actions docs (linked per claim below);
- GitHub Security Lab, [Preventing pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/);
- [benchmark-action/github-action-benchmark](https://github.com/benchmark-action/github-action-benchmark) README (as prior art, not a dependency); and
- this repo's `.github/workflows/ci.yml` and `bindings.yml`.

Scope: homegrown pipeline, informational only (no merge gating), PR results compared against a baseline stored from `main`. Three tiers: criterion micro-benches, end-to-end Rust benches, Node FFI overhead (Linux-x64-only in PR CI).

## Fork-PR security model

The whole design hangs on one fact: **a `pull_request` run whose head is a public fork gets a read-only `GITHUB_TOKEN` and no secrets, and the `permissions` key cannot raise it.** "If the workflow was triggered by a pull request event other than `pull_request_target` from a forked repository … the permissions are adjusted to change any write permissions to read only" and "you can use the `permissions` key to add and remove read permissions for forked repositories, but typically you can't grant write access" (the only exception is the admin-only "Send write tokens to workflows from pull requests" repo setting, which we should not enable) ([controlling permissions for GITHUB_TOKEN](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/controlling-permissions-for-github_token)). So a fork PR's bench job can never post a comment itself — `pull-requests: write` in its workflow is silently downgraded.

The three trigger options for getting a comment posted anyway:

| Trigger | Runs | Token on fork PR | Verdict |
| --- | --- | --- | --- |
| `pull_request` | PR merge commit, PR code | Read-only, no secrets ([docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/controlling-permissions-for-github_token)) | Safe place to *run* benches; cannot comment on fork PRs. |
| `pull_request_target` | Default-branch workflow file, default-branch context; "the `GITHUB_TOKEN` is granted read/write repository permission, even when it is triggered from a public fork" ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#pull_request_target)) | Read/write + secrets | Dangerous for benches: running benches means building and executing PR code (`build.rs`, proc macros, npm hooks) in a privileged context. GitHub: "Avoid using this event if you need to build or run code from the pull request" ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#pull_request_target)); the security-hardening guide says such workflows "must not explicitly check out untrusted code, including from pull request forks" and warns the combination "can be exploited to take over a repository" ([security hardening](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)). GHSL adds that even without touching secrets, checkout with default `persist-credentials: true` means "any running code can simply read the stored repository token from the disk" ([pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)). |
| `workflow_run` | Default-branch workflow file, on the default branch (`GITHUB_REF` = default branch); "is able to access secrets and write tokens, even if the previous workflow was not" ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_run)) | Read/write + secrets | The right privileged half — it never checks out or executes PR code. GitHub explicitly recommends it: "For privilege separation between workflows, `workflow_run` is a better trigger" ([security hardening](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)). |

### The artifact handoff

The pattern GHSL documents ([pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)): the unprivileged `pull_request` workflow should "store any results like code coverage or failed/passed tests in artifacts and exit"; a `workflow_run` workflow, "where it is granted write permission to the target repository and access to repository secrets," downloads them and comments. The `workflow_run` docs show exactly this — `actions/download-artifact` with `run-id: ${{ github.event.workflow_run.id }}`, `github-token: ${{ secrets.GITHUB_TOKEN }}`, and `permissions: actions: read` ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_run)).

Constraints and caveats:

- **Artifact contents are attacker-controlled.** "Artifacts resulting from untrusted PR data are themselves untrusted and should be treated as such when handled in privileged contexts" ([pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)); the hardening guide repeats it: workflows on `workflow_run` "should treat artifacts uploaded from other workflows with caution" ([security hardening](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)). Concretely: validate the PR number ("While the number itself is attacker controlled, it is an acceptable risk if the elevated workflow just comments on a PR" — still, cross-check it, see Recommendation), never execute anything from the artifact, and extract outside the workspace — the docs advise using `${{ runner.temp }}/artifacts`, "not … the workspace dir that may contain executable scripts" ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_run)).
- **The `workflow_run` workflow file must already be on `main`.** "This event will only trigger a workflow run if the workflow file exists on the default branch" ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_run)) — so the comment workflow can only be tested after merge, and PR edits to it do not take effect for that PR.
- It fires "regardless of the conclusion of the previous workflow"; gate on `github.event.workflow_run.conclusion == 'success'` ([events docs](https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows#workflow_run)).
- Cache poisoning is contained: low-trust triggers including `workflow_run` "get read-only access to default-branch caches" ([caching docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/caching-dependencies-to-speed-up-workflows)).

## Baseline storage options

| Option | Retention | Size | Write on merge to main | Read from a fork PR |
| --- | --- | --- | --- | --- |
| Dedicated data branch (gh-pages pattern) | Forever; full history | Git; trivially small for JSON | `git push` needs `contents: write`; races between concurrent main runs handled by a `concurrency` group or push retry | Plain `git fetch` of a public branch, no token needed |
| `actions/cache` | Evicted when "not accessed in over 7 days"; repo capped at 10 GB with oldest-access eviction ([caching docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/caching-dependencies-to-speed-up-workflows)) | Counts against the same 10 GB the rust-caches already fight over | Cache entries are immutable per key — save under a per-SHA key, restore by prefix | Works: PR runs "can restore caches created in … the default branch," "including base branches of forked repositories" ([caching docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/caching-dependencies-to-speed-up-workflows)); PR-saved caches are scoped to the merge ref and invisible to main, so forks cannot poison the baseline |
| Artifacts | 90 days by default (configurable 1–90 public / 1–400 private) ([repo settings docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)) | 500 MB free tier accounting aside, fine for JSON | Upload is per-run; no mutation problem | Painful: artifacts belong to a run, so fetching cross-run means "you need to supply a token and run identifier" ([artifact docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/storing-and-sharing-data-from-a-workflow)) — i.e., an API search for the latest successful main run first |

**Prior art — github-action-benchmark** stores exactly the dedicated-branch shape: it reads and updates `dev/bench/data.js` on `gh-pages` (`gh-pages-branch`, `benchmark-data-dir-path`), commits, and with `auto-push: true` pushes using the `GITHUB_TOKEN`; `alert-threshold` (default `200%`), `comment-on-alert`, and `comment-always` post commit/PR comments, and an `external-data-json-path` mode swaps the branch for an `actions/cache`-persisted JSON file ([README](https://github.com/benchmark-action/github-action-benchmark)). Its own README warns against its push step on PRs — "anyone who creates a pull request on your repository could modify your GitHub pages branch" — which is the same reason our PR job must be read-only and the baseline write must live in the push-to-main job.

**Why not `actions/cache` here:** this repo already hit the ceiling once — `ci.yml` saves rust-caches only on main because "per-branch saves pushed the repo to the 10 GB ceiling, and the resulting evictions cost more than the occasional cold PR build" (`.github/workflows/ci.yml`). A baseline in cache competes with those entries under oldest-access eviction, and a quiet week (>7 days without access) silently deletes it. A data branch has no eviction, gives per-main-commit provenance for free (one JSON file per baseline, keyed by SHA), and costs one small workflow step to update.

**Write concurrency on the data branch:** two merges to main close together can race their pushes. Serialize with a `concurrency` group on the baseline-writing job — "there can be at most one running job or workflow in a concurrency group at any time," with later runs `pending` ([concurrency docs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/control-the-concurrency-of-workflows-and-jobs)) — and keep a fetch/rebase/retry loop around the push as a belt-and-suspenders (the group serializes runs of *this* workflow, not any other writer).

**Merge-base caveat:** the PR job restores the *latest* baseline from main, which can be newer than the PR's merge-base. The comparison is then "PR head vs. current main," not "PR head vs. the main this PR branched from" — a regression on main since the branch point shows up in the PR's numbers. For an informational-only pipeline this is acceptable; the comment should print the baseline's main SHA so readers can tell. (Storing baselines per-SHA on the data branch leaves the door open to later resolving `git merge-base` and picking the closest ancestor baseline if it exists.)

## Comment hygiene

One sticky comment per PR, updated in place, identified by a hidden HTML marker in the body (e.g. `<!-- bench-comment -->`). Prior art: [marocchino/sticky-pull-request-comment](https://github.com/marocchino/sticky-pull-request-comment) ("Create a comment on a pull request, if it exists update that comment") keys on an invisible `header`, needs `pull-requests: write`, and accepts an explicit `number` input for non-PR-event use; [peter-evans/create-or-update-comment](https://github.com/peter-evans/create-or-update-comment) pairs with `find-comment` (`body-includes` a marker string) and its README concedes that "in *public* repositories this action does not work in `pull_request` workflows when triggered by forks."

Staying homegrown, the upsert is ~10 lines of `gh api` in the `workflow_run` job:

1. `gh api repos/$REPO/issues/$PR/comments --paginate` and `jq` for the first comment whose body contains the marker;
2. if found, `gh api -X PATCH repos/$REPO/issues/comments/$ID`; else `POST repos/$REPO/issues/$PR/comments`;
3. pass the body from the artifact file (`-F body=@comparison.md` after prepending the marker) — never interpolate artifact content into shell, per the script-injection guidance in the [security hardening guide](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions).

## Repo grounding

- `ci.yml` and `bindings.yml` both run `on: push: branches: [main]` + `on: pull_request`, set `permissions: contents: read` at workflow level, and use a `concurrency` group of `<name>-${{ github.ref }}` with `cancel-in-progress` only for PRs (main "keeps a full result for every merged commit"). A bench workflow should copy all three habits.
- `bindings.yml` is the path-filter precedent: identical `paths:` lists on `push` and `pull_request` scoping it to the FFI/bindings surface. The bench workflow gets the same treatment (bench sources + the crates they measure + the workflow files themselves), so doc-only PRs don't burn 20 minutes of benching.
- Runners are `ubuntu-latest`/`ubuntu-24.04` throughout — shared runners, so bench numbers are noisy; another reason the pipeline is informational-only and thresholds should be generous.
- `ci.yml` already builds one criterion bench (`cargo bench -p minip2p-core --bench multiaddr --no-run` in `lint`), so tier 1 exists; the Node FFI tier slots into the same Linux-x64 shape `bindings.yml` already uses.
- Growing `ci.yml` is the wrong move: its jobs are split precisely to keep the feature matrix off the critical path, and benches have different triggers (path filter), different permissions (the baseline writer needs `contents: write` on one job), and a privileged sibling workflow. Separate `bench.yml` + `bench-comment.yml`.

## Recommendation

Two workflows, three jobs.

**`bench.yml`** — `on: pull_request` (path-filtered like `bindings.yml`) + `on: push: branches: [main]` (same paths). Workflow-level `permissions: contents: read`. Concurrency `bench-${{ github.ref }}`, `cancel-in-progress` for PRs only.

- Job `bench` (both events): checkout, run the three tiers (criterion, e2e, Node FFI — all Linux-x64), emit one normalized `results.json`.
- Job `baseline` (`if: github.event_name == 'push'`, `needs: bench`, job-level `permissions: contents: write`, its own non-ref-keyed `concurrency: group: bench-baseline` so concurrent merges serialize): commit `results.json` as `<sha>.json` + move a `latest` pointer on a dedicated **`bench-data` branch**; push with a small rebase-retry loop. Chosen over `actions/cache` because of the repo's demonstrated 10 GB ceiling pressure and cache's 7-day-unused eviction; over artifacts because of 90-day expiry and awkward cross-run lookup (sources above).
- Job `compare` (`if: github.event_name == 'pull_request'`, `needs: bench`): fetch `bench-data`, read the latest baseline (works identically for fork PRs — read-only, public branch, no token gymnastics), render `comparison.md` including the baseline's main SHA and a stale-baseline note when that SHA isn't the PR's merge-base, and upload an artifact containing `comparison.md` + `pr-number`. No commenting here: on fork PRs the token is read-only by design and we don't enable the write-token setting.

**`bench-comment.yml`** — `on: workflow_run: workflows: ["Bench"], types: [completed]`. Workflow-level `permissions: actions: read, pull-requests: write`. Gate on `conclusion == 'success'`. Steps: download the artifact by `run-id: ${{ github.event.workflow_run.id }}` into `${{ runner.temp }}`; **validate** — PR number is an integer, and the PR fetched via `gh api` has `head.sha == github.event.workflow_run.head_sha` (defeats PR-number spoofing; artifact data is untrusted input per GHSL/GitHub docs above); then the marker-based `gh api` upsert of the single sticky comment. Never execute or `source` anything from the artifact; pass the body as a file.

Fork PRs work end to end with zero secrets exposed to PR code; same-repo PRs take the identical path, so there is one code path to maintain. Known limits, stated in the comment itself: shared-runner noise, and the baseline may be newer than the merge-base (informational only, so acceptable). Remember the `workflow_run` bootstrap rule: `bench-comment.yml` only functions once merged to `main`.
