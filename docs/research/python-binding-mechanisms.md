# Python binding mechanisms over `minip2p-ffi-core`

Research for a Python SDK binding decision, sibling of the Node decision in [ADR 0001](../adr/0001-napi-rs-for-node-bindings.md) and the shell layout in [ADR 0002](../adr/0002-extract-ffi-core-binding-shells.md). The question: which of **A. UniFFI Python (reuse `crates/ffi`)**, **B. BoltFFI Python (new shell)**, or **C. hand-written PyO3 shell** should carry `@minip2p`-for-Python over the binding-agnostic core.

## Decision

**Recommend C: a hand-written PyO3 shell (`crates/python`, `publish = false`) packaged with maturin as `abi3-py310` wheels.** Rank: C > A > B.

The deciding constraints come from `ffi-core`'s shape, not from raw call speed:

1. **The doorbell rings from a Rust thread and `wait_stopped` blocks.** `ffi-core` spawns a dedicated `minip2p-doorbell` thread and feeds it through a `sync_channel(1)` with `try_send`, so the driver never blocks on delivery ([`endpoint.rs#L161-L169`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/crates/ffi-core/src/endpoint.rs#L161-L169), [`#L765-L795`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/crates/ffi-core/src/endpoint.rs#L765-L795)). `wait_stopped` waits until that thread has exited ([`#L451-L470`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/crates/ffi-core/src/endpoint.rs#L451-L470)), which requires the thread to finish any in-flight `on_events_ready` call, which requires the GIL. A binding that holds the GIL across `wait_stopped` therefore stalls the whole interpreter for the full timeout and then returns `false`. BoltFFI's generated extension never releases the GIL; UniFFI's ctypes path releases it by default; PyO3 releases it only where the shell says so. Only C makes the release explicit and testable per call.
2. **Free-threaded Python.** ctypes and PyO3 (0.28+) mark their modules GIL-free; BoltFFI's generated module uses single-phase init with no `Py_mod_gil`/`PyUnstable_Module_SetGIL`, so importing it re-enables the GIL with a `RuntimeWarning`.
3. **Packaging.** maturin gives C one abi3 wheel per platform with manylinux/musllinux handling and a `generate-ci` matrix; A gets the same via `bindings = "uniffi"` (universal `py3-none-<platform>` tags); B's `pack python` shells out to `pip wheel` on the host, refuses `cargo --target`, and has no manylinux, auditwheel, or abi3 handling.
4. **The `uniffi =0.31.2` pin.** A would extend the mobile-only pin to Python, the exact coupling ADR 0001 and 0002 avoided for Node; C and B keep it mobile-only.
5. **`unsafe` policy.** PyO3 ships a `#![forbid(unsafe_code)]` UI test that passes over `#[pyclass]`/`#[pymodule]`/`#[pyfunction]`, so the shell can inherit the workspace `forbid` unchanged (better than `crates/nodejs`, which had to lower to `deny`). BoltFFI's expansion contains many `unsafe` blocks and has no equivalent test; A is annotation-free for Python because the shell already exists.

A is the credible fallback: zero new Rust, but ctypes call overhead plus a per-byte Python loop on the `bytes` lowering path, and the pin. B is rejected for the same category of reason ADR 0001 rejected it for Node: the mechanism does not fit `ffi-core`'s threading model today, and the project is too young to bet a second binding surface on.

### GIL and threads

The relevant facts about `ffi-core`: the doorbell callback executes on the Rust `minip2p-doorbell` thread, never on a Python-created thread; the callback is wrapped in `catch_unwind` on both the driver and doorbell threads ([`driver.rs#L346-L350`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/crates/ffi-core/src/driver.rs#L346-L350), [`endpoint.rs#L777`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/crates/ffi-core/src/endpoint.rs#L777)); `drain_events`, `stop`, and every command take a short `Mutex` and return; only `wait_stopped` blocks, and it already refuses to wait from the driver or doorbell thread ([`#L462-L466`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/crates/ffi-core/src/endpoint.rs#L462-L466)). CPython requires any C-created thread to acquire an attached thread state (`PyGILState_Ensure`) before touching the C API ([`init.rst#L1037-L1051`](https://github.com/python/cpython/blob/ac991beb29b1783316c4016c99468c008568d08a/Doc/c-api/init.rst#L1037-L1051), [`#L1292-L1312`](https://github.com/python/cpython/blob/ac991beb29b1783316c4016c99468c008568d08a/Doc/c-api/init.rst#L1292-L1312)).

### Async story (asyncio consuming doorbell + drain)

All three end in the same Python adapter, which is the shape `bindings/ts/node/src/adapter.ts` already uses ([`EventDrain`](https://github.com/deepso7/minip2p/blob/e41844ca85322cc0988a8f5cf4a26b8cfbf89ad7/bindings/ts/node/src/adapter.ts#L561-L625)): the doorbell hands off to the loop with `loop.call_soon_threadsafe` (the documented thread-safe scheduling primitive, [asyncio docs](https://docs.python.org/3/library/asyncio-eventloop.html#asyncio.loop.call_soon_threadsafe)); the loop-side task calls `drain_events(256)`, dispatches, and yields with `await asyncio.sleep(0)` (or `loop.call_soon`) between non-empty batches until a drain returns empty. ADR 0003's lost-wakeup rule (drain until empty after every ring) is preserved unchanged.

- **A**: the Python doorbell class implements the generated `P2pEventDoorbell` protocol; ctypes ensures the GIL on the Rust thread. UniFFI's own async runtime uses the identical `call_soon_threadsafe` continuation ([`Async.py#L36-L44`](https://github.com/mozilla/uniffi-rs/blob/05b45b110f652d58d94c653992aeb3adc3a094f4/uniffi_bindgen/src/bindings/python/templates/Async.py#L36-L44)).
- **B**: same protocol object; BoltFFI's future waker also uses `call_soon_threadsafe` from a `PyGILState_Ensure` block ([`native_module.c#L472-L490`](https://github.com/boltffi/boltffi/blob/f5c905755d68e7a8161fa10481edc282040ec27e/boltffi_backend/templates/target/python/native_module.c#L472-L490)). BoltFFI's own `ffi_stream` type offers `wait(ms)`/`pop_batch()` in Python ([streaming.mdx](https://github.com/boltffi/boltffi/blob/f5c905755d68e7a8161fa10481edc282040ec27e/docs/src/content/docs/streaming.mdx)), but adopting it would replace `ffi-core`'s carry with a second queue, the design ADR 0003 rejected.
- **C**: the shell's `EventDoorbell` impl holds `Py<PyAny>` for the loop and the callable and calls `loop.call_soon_threadsafe(cb)` under `Python::try_attach`; the drain method is a plain sync `#[pymethods]` call. PyO3's `async fn` support is experimental and asyncio-only ([async-await.md](https://github.com/PyO3/pyo3/blob/a70d17f898df41b3d1632ee987f624f5222d8d39/guide/src/async-await.md)) and is not needed for this model.

## Risks of the recommendation and mitigations

1. **A forgotten `detach` reintroduces the GIL stall.** Mitigation: the shell wraps `wait_stopped` (the only blocking call) in `py.detach`; one pytest starts an endpoint, rings the doorbell from a Rust test hook or by generating traffic, and asserts `wait_stopped` completes while a Python doorbell callback is pending.
2. **PyO3 0.x minors break roughly three times a year.** Mitigation: pin `pyo3 = "=0.29.2"` exactly as `napi` is pinned, keep the shell thin so migrations are mechanical.
3. **Three shells to keep in sync with `ffi-core`.** Mitigation: same as ADR 0002; drift fails to compile. Reuse `crates/nodejs`'s serde-based event flattening if it is cheaper than a second hand-written converter.
4. **Free-threaded wheel matrix grows** (`abi3` + `cp314t` + `abi3t`). Mitigation: ship `abi3-py310` first; add `cp314t` only when a user asks, and `abi3t` once CI has a 3.15 interpreter. maturin documents the split build ([bindings.md#L25-L45](https://github.com/PyO3/maturin/blob/6b996551089beb9c19aff17d7fc86700a7942ebd/guide/src/bindings.md#L25-L45)).
5. **Doorbell fires during interpreter shutdown.** Mitigation: use `Python::try_attach` in the doorbell and drop the ring when it returns `None`; `ffi-core` already tolerates callback unwinds.
6. **CI cost of seven platform builds.** Mitigation: same target list as the napi job, driven by maturin-action with `manylinux: 2014` and `musllinux_1_2`, gated behind the existing `bindings-native.yml` schedule for non-release runs.

## What a first slice looks like
