# Relay-server compatibility envelope

Research for [Audit the relay-server compatibility envelope](https://github.com/deepso7/minip2p/issues/62), pinned to:

- rust-libp2p `libp2p-relay` 0.22 source at [`170c3c81ddd80e7c58b0500563e00a09139e8545`](https://github.com/libp2p/rust-libp2p/tree/170c3c81ddd80e7c58b0500563e00a09139e8545/protocols/relay);
- Circuit Relay v2 revision at [`6b6203ee6f62938ce67efdb33498173f475851c0`](https://github.com/libp2p/specs/blob/6b6203ee6f62938ce67efdb33498173f475851c0/relay/circuit-v2.md); and
- minip2p at [`bc73dc6af3f0420318c7422028abd4289b5ffaba`](https://github.com/deepso7/minip2p/tree/bc73dc6af3f0420318c7422028abd4289b5ffaba).

## Decision

The seed is a sound architectural starting point, but it is **not yet a rust-libp2p-parity specification**. Keep rust-libp2p 0.22 as the operational baseline, while explicitly separating three contracts:

1. Circuit Relay v2 wire requirements;
2. observable behavior of the pinned rust-libp2p implementation; and
3. intentional minip2p behavior required by its sans-I/O, single-connection swarm.

The seed already identifies several intentional differences, but it also contains five material parity contradictions: its HOP enablement is static rather than dynamically advertised, its address source is listeners rather than confirmed external addresses, its byte-limit rule matches neither the protocol nor rust-libp2p exactly, it misidentifies rust-libp2p's worker cap as a pre-negotiation cap, and it collapses reservation expiry and connection closure into one event. Those points must be resolved by the remaining Wayfinder tickets before the four-PR plan can be approved.

## Admission order if the seed policy is retained

If the later public-contract decision retains the seed's rate-first policy, the revised spec should state the exact order rather than saying “rust-libp2p semantics”:

1. reject administratively unavailable service according to the chosen HOP-advertisement model;
2. charge peer then IP rate limiters (short-circuiting means a peer token can be consumed when the IP limiter denies);
3. apply corrected per-peer and global would-exceed capacity checks, treating same-connection renewal as replacement;
4. for CONNECT, look up the destination's exact live reservation only after resource admission; and
5. count an accepted-but-not-yet-bridged STOP attempt against circuit capacity until it resolves.

This is the coherent interpretation of the seed's current text; changing back to rust-libp2p's capacity-first order remains a valid choice for the later contract ticket.

## Required edits before approval

1. Replace “matching rust-libp2p semantics” and “full limits parity” with a scoped compatibility statement referencing the deviation inventory below.
2. Resolve reservation cardinality and reachability/HOP advertisement before freezing public APIs; both may require Swarm changes already held in the map's fog.
3. Rewrite byte-limit semantics after choosing the contract. The current “one-chunk overshoot matches rust-libp2p” statement is false.
4. Correct the worker-cap description: rust-libp2p's cap is post-multistream, does not cover the full request decision, and has a separate outbound STOP set that the seed does not yet match.
5. Preserve expiry versus disconnection in reservation events, preferably as a close reason; define exactly-once terminal circuit events and byte reporting.
6. Add an explicit deviations section covering: single connection per peer; corrected cap and renewal boundaries; admission order; static or dynamic HOP model; address source/filtering; 8 KiB frames; semantic-error responses; zero-duration behavior; combined-versus-directional byte accounting; richer lifecycle events; and action-based forwarding/backpressure.

With those corrections, the remaining crate boundary, sans-I/O action model, exact stream keys, STOP status mapping, default numeric limits, token-bucket defaults, relayed-HOP refusal, and four-PR staging are suitable inputs to the later public-contract and final-approval tickets.
